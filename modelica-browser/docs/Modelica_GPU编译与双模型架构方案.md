# Modelica GPU 编译与双模型架构方案

状态：方案讨论稿，当前不进入具体实施
日期：2026-10-10

## 1. 目标与边界

本方案研究如何以 Modelica 作为机器人统一物理建模语言，并为大规模强化学习生成能够在 GPU 上真正获得吞吐收益的仿真程序。它不假定普通 OMC C 程序或 FMU 可以直接在 GPU 上执行，也不把“生成 CUDA 语句”等同于完成 GPU 仿真后端。

当前只确定约束、候选架构和决策门。GPU 编译器、训练接口、VectorEnv、强化学习算法和训练套件均不在当前 P6 实施范围内。

## 2. 基本判断

Modelica 是声明式方程建模语言。模型描述组件、连接、参数、连续方程和离散行为；编译器负责连接展开、状态选择、方程匹配、索引约简、代数消元、计算调度、数值算法选择和目标代码生成。

GPU 能力需要三个条件同时成立：

```text
受限且可静态分析的 Modelica 模型
              +
有界、批量化的数值算法
              +
面向环境维度的 GPU 编译器与运行时
```

单个机器人通常不足以填满 GPU。主要并行维度应是结构相同的环境批次，而不是把一台机器人内部少量方程机械拆给大量线程：

```text
state[environment, stateIndex]
parameter[environment, parameterIndex]
action[environment, actionIndex]
```

## 3. 真正获得 GPU 加速的模型要求

### 3.1 结构和数据要求

- 一个批次内的机器人拓扑、自由度、数组尺寸和接口完全相同；
- 刚体、关节、执行器、传感器以及接触工作区容量在编译期确定；
- 状态、参数、动作和输出使用固定 shape、明确 dtype 和连续的批量布局；
- 质量、惯量、阻尼、摩擦、供电和传感器误差等运行参数可以按环境变化，但不能改变张量 shape；
- 每个物理步的状态、接触缓存、观测、奖励和终止标志保持在设备端；
- step 内禁止文件访问、字符串处理、动态内存分配和逐环境主机回调；
- 日志、渲染和审计变量只按批次或低频抽样，不在每一步复制到 CPU。

### 3.2 方程要求

首期可支持：

- 显式 ODE；
- 编译期能够消除的代数方程；
- 固定规模小型线性系统；
- 固定规模、固定最大迭代次数的非线性系统；
- 固定维度的矩阵、空间向量和刚体运算；
- 连续函数或可转换为有界 mask 的分段函数。

首期不支持：

- 任意高指数 DAE；
- 运行时改变规模的代数系统；
- 不定次数 Newton、事件或约束迭代；
- 运行期重新做状态选择和结构变换；
- 动态创建、删除或重连组件；
- 没有 GPU 等价实现的外部函数和 `ExternalObject`。

### 3.3 时间和事件要求

- 物理步长固定，控制、传感器和慢速热状态采用整数倍多速率调度；
- 动作在控制周期内明确保持或插值；
- 饱和、软限位、保护状态和回合终止优先转换为设备端 mask；
- 状态机的状态数、转换数和每步最大处理次数必须有界；
- 不允许每个环境独立执行复杂零点定位或改变方程结构；
- 数值失败以稳定错误码和终止 mask 表达，不能阻塞整个批次。

### 3.4 获得实际加速的运行条件

- 并行环境数足以摊销编译、模型上传和 kernel 启动；
- 每步计算量与内存访问比足够高，避免大量零散小 kernel；
- 编译器能够融合相邻逐元素方程并减少全局内存往返；
- 接触候选和约束数量有上限，批次之间分支差异可控；
- reset、随机化、观测、奖励和策略推理也在 GPU 上完成；
- 训练主循环没有逐步的 device-to-host 同步；
- 性能结论使用端到端 `transition/s`、显存、GPU 利用率和 p50/p95 step 时间验证，而不是只测一个方程 kernel。

## 4. 数值算法要求

### 4.1 首期积分器

优先支持固定步长显式 Euler、半隐式 Euler、RK2/RK4，以及针对机械系统的专用积分。通用变步长 DASSL、IDA 和每环境独立选阶的 BDF 不进入首期 GPU Profile。

如果后续增加隐式积分，需要固定稀疏结构、批量 Jacobian、批量线性求解和固定最大迭代次数。未收敛环境由 mask 隔离，不能让单个环境控制整个 GPU 批次的循环次数。

### 4.2 多刚体和接触

树形多刚体运动学、惯量传播和关节动力学适合固定拓扑批处理。碰撞和接触需要专用 GPU 算子，包括宽相位、窄相位、接触流形、摩擦和约束求解。编译器应识别 AIDCRobotics 标准接触组件并将其降低为这些算子，不依赖从展开后的低层标量方程中重新识别接触算法。

接触是本方案的主要技术风险。完成 CUDA 代码生成不等于已经具备稳定、可信且高吞吐的机器人接触求解器。

## 5. 推荐编译架构

### 5.1 三条候选路线

| 路线 | 做法 | 优点 | 主要代价 |
|---|---|---|---|
| 修改 OMC | 在 OMC 内增加 GPU IR、代码生成目标和运行时 | 复用完整语言前端和符号后端 | 深度依赖 OMC 内部结构，上游同步和维护成本高 |
| OMC 前端加 AIDC GPU 后端 | OMC 完成解析、展开和符号预处理，AIDC 接收规范化 IR | 复用语言语义，同时控制 GPU 算法与运行时 | 需要稳定 IR 边界，可能维护小型 OMC 补丁 |
| 自研受限编译器 | 只实现 AIDCRobotics 使用的 Modelica 子集 | 范围和 GPU 设计完全可控 | 继承、修改、连接展开和方程匹配仍然复杂 |

首选路线是“OMC 前端加 AIDC GPU 后端”。原型期可以使用 OMC 导出的规范化表示验证 GPU IR；接口稳定后，再决定把后端集成为 `--simCodeTarget=AIDCGPU`，还是保持独立编译器进程。

### 5.2 编译流水线

```text
Modelica source
  -> OMC parse/type/instantiate/flatten
  -> connection expansion and symbolic preprocessing
  -> AIDC GPU Profile eligibility pass
  -> normalized AIDC GPU IR
  -> equation partition and schedule
  -> environment-batch vectorization
  -> kernel fusion and memory planning
  -> CUDA / Warp / other device code
  -> AIDC GPU runtime
```

编译器必须在生成代码前给出资格报告，列出可直接编译的方程、应用的降阶组件、不支持的语义、重新编译所需的结构参数、估计显存和可能的主机同步点。不支持的模型必须失败并精确定位，不允许静默改变语义。

### 5.3 GPU IR

GPU IR 至少包含：

```text
Model
├─ constants
├─ structuralParameters
├─ episodeParameters[env, ...]
├─ continuousState[env, ...]
├─ discreteState[env, ...]
├─ inputs/outputs[env, ...]
├─ initializationGraph
├─ continuousEquationGraph
├─ discreteTransitionGraph
├─ multibodyOperations
├─ contactOperations
└─ solverConfiguration
```

IR 应独立于 CUDA 文本，允许先生成 Warp 原型，再根据性能决定是否生成原生 CUDA、Triton 或其他设备代码。

## 6. 双模型架构

执行上允许存在两个数学 Profile，但不允许存在两份独立机器人事实源：

```text
统一 Robot IR、参数记录和接口契约
│
├─ VerificationPlant
│  ├─ 完整 Modelica
│  ├─ OMC CPU/FMU
│  ├─ DAE、变步长和完整事件
│  └─ 电气、热、故障和详细审计
│
└─ TrainingPlant
   ├─ GPU 固定步长
   ├─ 批量多刚体和接触
   ├─ 降阶执行器、电池与热模型
   └─ 设备端 reset、观测和终止
```

两者必须共享稳定 ID、坐标系、单位、拓扑、质量惯量、关节、设备标称参数、动作与观测顺序、时间契约和参数来源。允许不同的是求解器、接触实现、高频设备细节、事件实现和输出变量数量。

AIDCRobotics 使用 `replaceable/redeclare` 或等价 Profile 配置组合详细组件和 GPU 组件。所有替换写入 `fidelity-manifest.json`，记录原组件、替代组件、删除的状态或事件、参数映射、有效范围、标定场景、误差和越界行为。

## 7. 可简化与必须保留的物理

训练模型必须保留会改变策略最优行为的因素，包括质量惯量、关节方向与限位、执行器转矩速度边界、控制延迟与带宽、电流限制与压降、主要摩擦阻尼、足底接触和策略实际使用的传感器。

可按证据降阶的内容包括 PWM 开关、详细电源开关网络、高频电气状态、复杂热网络、齿轮微观接触、CAD 三角网格和仅用于工程审计的内部变量。可采用平均模型、低阶状态空间、查表、分段多项式或由 VerificationPlant/实测数据校准的代理模型。

简化接受标准是：在声明的工况域内不会让策略学习到高保真模型或实机中不存在的优势。只要可能改变策略行为，就必须保留、随机化或加入发布门禁。

## 8. 与现有后端的关系

普通 `omc -> C/可执行程序/FMU` 仍是 CPU 高保真路径。Modelica 外部 C/C++ 几何库解决几何查询和资源复用，不会使完整求解器自动成为 GPU 程序。

在 AIDC GPU 编译后端通过接触、数值和训练吞吐门禁之前，MuJoCo Warp 可以继续承担现有 GPU 训练物理采样。它是迁移和对照后端，不是机器人参数事实源。

## 9. 后续研究阶段与决策门

| 阶段 | 范围 | 继续条件 |
|---|---|---|
| G0 | 单关节、无接触、固定步长、批量环境 | 与 OMC CPU 全轨迹误差受控，并相对 CPU 获得明确端到端加速 |
| G1 | 固定拓扑树形多刚体 | 运动学、能量和关节动力学门禁通过 |
| G2 | 平面接触、摩擦、限位和落地 | 接触稳定性、冲量、滑移和失败率通过 |
| G3 | 执行器、电池、热、传感器 TrainingPlant | fidelity manifest 完整，工作域内误差满足门槛 |
| G4 | GPU VectorEnv 和训练接入 | reset/step/observation 无逐步主机同步，训练结果可复现 |
| G5 | 扩展事件、隐式系统和更多组件 | 每项语义有 CPU 对照和独立性能收益证据 |

G0 之前不修改正式训练路线；G2 之前不宣称能够替代机器人接触后端；G4 之前不宣称能够替代 MuJoCo Warp 训练运行时。每一阶段都必须同时提供数值一致性和端到端性能证据。

## 10. 当前决策

1. 当前不实施 GPU 编译器和训练接口。
2. P6 先完成 P0～P5 模型生成、OMC 编译、仿真、打包和便携复跑的闭环验收。
3. 保留 Modelica 作为统一建模语言、OMC 作为标准 CPU 编译与验证后端。
4. GPU 编译研究以受限 `AIDCRobotics.GPUProfile` 为前提，不承诺支持任意 Modelica。
5. 后续立项时先执行 G0，以实测误差和端到端加速比决定是否继续。
