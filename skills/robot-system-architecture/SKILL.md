# 机器人系统架构设计

把已经确认的机器人需求转化为可评审、可计算、可继续进入总体布局的系统方案。主要交付物是一个简洁的 `architecture.sysml`；需求仍由 `requirements.sysml` 管理，空间几何仍由 CAD 管理。

开始新方案或大范围重构前，阅读[业务流程](references/workflow.md)和[SysML 编写规则](references/sysml-authoring.md)。准备 CAD 交接或评审装配可行性时，再阅读[初步布局检查清单](references/preliminary-layout-checklist.md)。遇到输入缺失、需求冲突或单位问题时，按[异常场景处理](references/acceptance-scenarios.md)执行。

需要语法起点时参考[十轴步行机器人架构样例](assets/walking-robot-architecture-example.sysml)。该文件用于展示结构，不代表用户项目的部件、数值或已验证结论。

## 保持事实边界

- 从 `requirements.sysml` 提取会驱动架构的任务、工况、接口、安全行为和定量门槛，不修改或重新解释已批准需求。
- 区分厂家数据、实测值、计算值、规划估计和方案假设。无法确认的数据保持缺失，并列为待验证项。
- 不猜测质量、尺寸、孔位、轴线、电池容量、电流、功耗、控制周期、协议或安全阈值。
- `architecture.sysml` 记录逻辑组成、接口、连接、原始参数、计算和装配交接标识；不要把详细几何、审批流或项目进度塞入模型。
- 不修改 SysML 浏览器、Parser Runtime 或其他产品代码，也不把当前机器人的业务规则固化进软件。

## 形成方案

新建系统架构时至少提出两个完整候选方案。每个方案都要覆盖运动形式与自由度、执行器、控制与计算、传感器、供电、通信、结构组成、装配风险和验证工作，不能只比较单个零件。

围绕需求逐项比较候选方案，明确假设、优势、代价、关键风险和仍缺少的证据。选定方案后说明淘汰其他方案的关键原因。若只是修改已选架构中的局部内容，保留既有方案决策，除非变更已经使其失效。

## 创建架构模型

默认只创建或修改一个 `architecture.sysml`：

1. 建立一个根 Package、必要的端口定义、可复用部件定义和一个顶层系统定义。
2. 为每个有名称、会出现在模型树或视图中的业务元素，在元素体内声明简短中文名称 `doc /* 中文名称 */`；英文声明名继续作为稳定引用，不翻译、不替换。
3. 按真实装配责任建立系统、子系统和关键设备的父子组成，不按学科复制另一棵结构树。
4. 为主要部件分配跨 SysML、CAD、BOM 和验证稳定的 `componentId`。
5. 声明有业务意义的端口和明确的两端连接。
6. 把原始参数放在实际所属部件上，物理量使用标准类型和显式单位。
7. 使用 `calc def`、计算调用、实际参数绑定和约束建立质量、续航/能量、峰值供电、控制时序等项目需要的分析。
8. 只有模型确实需要表格浏览时，才声明对应的 SysML Table View；列标题、行和顺序由模型定义。
9. 为需要进入总体布局的部件记录父装配、固定或运动关系、关节/安装接口、来源状态和 `cadRef`。

字段和当前 Parser 兼容写法见[SysML 编写规则](references/sysml-authoring.md)。

## 交付前验证

- 模型只有一个根 Package，且能由项目的 SysML Parser 解析。
- 每个命名业务元素都有简短中文 `doc /* … */`；浏览器显示中文名称，同时保留英文标识符用于引用和追溯。
- 部件 ID 唯一，左右件、运动件和装配件不会混淆。
- 每条连接都有真实存在的两个端点。
- 所有物理量都有类型和单位；比较两侧量纲兼容。
- 派生结果只由计算生成，不与手工填写的结果并存。
- 缺失输入不会按零计算，也不会显示伪造的精确结果。
- 需求冲突已经显式列出，不通过任意选值掩盖。
- 规划估计和方案假设没有被描述成厂家数据或实测结果。
- CAD 引用只表示交接目标；不存在的实体、干涉检查和安装验证不得写成已经完成。
- 架构说明包含仍待确认的输入、未关闭风险和下一步验证任务。

交付前调用 `aidc_sysml_validate`；需要查看架构图时调用 `aidc_sysml_open`。没有 MCP 的 CI 环境使用对应的 `aidc sysml validate/open` 命令。
